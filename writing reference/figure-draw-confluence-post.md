# Figure Draw 개발 완료 — 소환서 인터랙션부터 iPad 영상 재생 개선까지

> 사내 피규어 배포 이벤트를 위한 PWA 개발 및 개선 기록
>
> 기준일: 2026-09-18 · 최종 기능 버전: figure-v32 · 상태: 배포 및 사용자 확인 완료

## 한눈에 보는 결과

기존 KUJI 앱을 기반으로, 피규어 추첨 과정을 소환서와 영상 연출로 경험할 수 있는 Figure Draw를 정리했습니다. 드래그 안내, iPad 영상·오디오 호환성, 추첨 운영 규칙과 공유 자료를 보완했으며, 마지막으로 메인 및 미당첨 화면에서 반복되던 영상 시작 지연을 개선했습니다.

최신 v32 배포 후 사용자가 전체 확인 완료를 전달했습니다. 이번 글에서는 실제 적용한 방식과 검증 범위를 중심으로 주요 작업을 공유합니다.

- [앱 실행](https://ssuperwasabi.github.io/event-game-figure-draw/app/)
- [GitHub 저장소 및 사용 안내](https://github.com/SSuperWasabi/event-game-figure-draw)

## 1. 이벤트 경험을 소환서 중심으로 구성

앱의 기본 흐름은 **메인 → 소환서 드래그 또는 자동 오픈 → 소환 연출 → 결과 → 메인 복귀**입니다.

소환서를 오른쪽으로 밀면 영상이 진행되고, 되돌리거나 취소하면 해당 상태에 맞춰 반응하도록 구성했습니다. 조작을 완료하기 전에 추첨되거나 재고가 차감되지 않도록 관련 경로를 확인했습니다. 직접 드래그하기 어려운 경우를 위한 자동 오픈도 유지했습니다.

영상 비율에 따른 타이틀 배치와 안내 문구를 다듬고, 관리자 설정을 통해 행사 진행에 맞는 화면 흐름을 선택할 수 있도록 했습니다.

## 2. 화살표는 방향을 안내하고, 핸들은 사용자를 기다리도록

드래그 안내에서 중요한 것은 화려한 움직임보다 “어디를 잡고 어느 방향으로 움직이는지”가 명확한 것입니다.

안내 UI를 소환서 박스 내부 하단에 넣고, 보라색 핸들과 골드 화살표를 적용했습니다. 레일 화살표는 10개로 늘리고 선 두께를 1.5배로 보강했습니다. 자동 오픈 버튼 위 안내 문구도 기존 대비 50% 키워 읽기 쉽게 했습니다.

최종 동작은 다음과 같습니다.

- 대기 중에는 핸들이 왼쪽 출발점에 고정됩니다.
- 골드 화살표만 자동차의 시퀀스 방향지시등처럼 왼쪽에서 오른쪽으로 순차 점등합니다.
- 사용자가 실제로 드래그할 때 핸들이 진행도를 따라 움직입니다.

이를 통해 자동으로 움직이는 장식과 사용자가 움직여야 하는 조작 대상을 혼동하지 않도록 했습니다.

## 3. iPad 호환성은 영상과 오디오를 나누어 점검

iPad의 재생 문제는 여러 버전을 비교해 영상 준비, 인코딩, 오디오 처리의 영향을 구분했습니다. 소환서 영상은 확인된 호환성 문제에 맞춰 H.264 타이밍과 인코딩을 보완했습니다.

BGM과 효과음은 Web Audio 경로를 정리해 소환 시 BGM 볼륨을 낮추고, 화면 전환이나 자동 오픈 이후에도 효과음과 배경음이 자연스럽게 이어지도록 했습니다.

이 과정에서 얻은 기준은 “영상이 늦다”는 증상을 곧바로 파일 크기 하나의 문제로 보지 않는 것입니다. 데이터 읽기, 영상 요소 연결, 디코딩, 실제 재생 시작은 서로 다른 단계이므로 각각 확인해야 했습니다.

## 4. 메인 영상: 늦게 나온 화면을 가리는 대신 다음 영상을 미리 준비

메인 화면의 목표는 명확했습니다. **메인에 돌아오는 순간부터 다음 영상이 보여야 한다**는 것입니다.

초기에는 영상 읽기 우선순위를 조정하고 포스터로 시작 지연을 가리는 방식도 시도했습니다. 하지만 포스터나 이전 영상이 잠깐 보였다가 다음 영상으로 바뀌는 경험은 요청한 품질에 맞지 않았습니다. 해당 방식은 최종안에서 제외했습니다.

v31에서는 두 개의 고정 영상 플레이어를 이용해 다음 영상의 시작 프레임을 화면 복귀 전에 준비하도록 바꿨습니다. 준비된 플레이어를 그대로 사용하므로 복귀 순간에 소스를 다시 연결하거나 영상을 다시 로드하는 비용을 줄였습니다. 숨은 영상을 계속 재생하는 방식이 아니라 필요한 준비를 마친 상태로 관리합니다.

메인 영상의 중복 없는 셔플도 유지했습니다. 또한 배경 효과 때문에 같은 영상을 중복 재생하던 부분은 정리했습니다. 레터박스 배경용 정지 이미지와 화면 시작을 대신하는 전경 포스터는 서로 다른 용도이며, 전경 포스터 방식은 최종 해결책에 포함하지 않았습니다.

## 5. 미당첨 영상: 한 종류의 영상을 매번 새로 준비하지 않도록

미당첨 영상은 한 종류인데도 결과 화면마다 늦게 나타나는 문제가 있었습니다. 확인 결과, 화면 진입 때 미디어를 읽고 새 영상 요소를 준비한 뒤 화면을 떠날 때 해제하는 반복 비용이 있었습니다.

v32에서는 단일 미당첨 영상 플레이어를 유지하고 다음 결과 화면에서 재사용하도록 바꿨습니다. 메인 영상 준비를 우선 처리한 뒤 미당첨 영상을 사전 준비하며, 파일이나 설정이 바뀌면 오래된 준비 작업을 무효화합니다.

화면 밖의 영상이 보이거나 불필요한 UI 애니메이션이 실행되지 않도록 비활성 처리도 추가했습니다. 여러 영상처럼 최적화 조건에 맞지 않는 경우는 기존 처리 경로를 사용합니다.

## 6. 기존 운영 기능을 보존하며 검증

영상 개선 때문에 추첨 결과나 운영 흐름이 바뀌지 않도록 함께 점검했습니다.

- 재고 비례 추첨, 선택적 고정 확률, 쿨다운과 구간 배분 등 추첨 설정
- 상품 재고와 추첨 로그 저장 및 실패 처리
- 드래그 중도 취소와 자동 오픈
- BGM, 효과음, 음소거
- 결과 팝업과 결과 진입 기준 5초 자동 복귀
- 메인 영상 순서 및 미디어 교체 시 준비 취소

검증 결과는 자동화 측정과 사용자 확인을 구분해 기록했습니다.

| 구분 | 확인 내용 |
| --- | --- |
| 규칙·화면·오디오·PWA | 관련 자동화 테스트 통과 |
| 메인 영상 / Chrome | 실제 영상으로 준비 후 12회 복귀, 불필요한 load/seek/waiting 없음 |
| 미당첨 영상 / Chrome | 실제 영상으로 10회 재진입, 데이터 읽기 1회 및 동일 플레이어 재사용 확인 |
| 배포 | v32 커밋과 GitHub Pages 게시 파일 일치 확인 |
| 사용자 테스트 | 2026-09-18 전체 확인 완료 피드백 수신 |

Chrome 측정 횟수는 iPad 계측값이 아닙니다. 사용자 확인으로 최종 테스트 결과를 기록하되, 모든 기기와 메모리 상태에서 지연이 전혀 없다는 의미로 확대하지 않습니다. 첫 실행, 저장소 정리 직후, 브라우저의 미디어 리소스 회수 상황은 후속 관찰 대상입니다.

## 7. 타 부서 공유와 인수인계

프로젝트 작업 폴더는 F: 드라이브로 이전했으며, 이미지·영상 등 리소스를 종류별로 정리했습니다. 최종 적용 파일은 `final-assets`, 이전 후보는 `-old`로 구분했습니다. 메인 루핑과 미당첨에 실제 사용되는 영상은 최종 자산으로 관리합니다.

README와 작업 일지에는 사용·배포·검증 이력을 남겼습니다. 전체 과정은 별도 writing reference로 정리해 후속 담당자가 최종 결정의 이유를 확인할 수 있도록 했습니다.

공유 시에는 다음 사항을 함께 안내해야 합니다.

1. 앱 실행 링크와 소스 코드 저장소를 구분해 전달합니다.
2. 운영 데이터와 대용량 미디어는 GitHub 소스만으로 모두 전달되지 않으므로 백업 및 포함 파일을 확인합니다.
3. 여러 기기의 재고와 추첨 기록이 자동 동기화되는 중앙 서버 서비스는 아닙니다.
4. 운영 중 사이트 데이터를 무작정 삭제하지 않도록 주의합니다.
5. 기존 v28 공유 ZIP은 이번 문서 정리에서 재생성하지 않았으므로 최신 v32 패키지로 전달하지 않습니다.

## 마무리

이번 개선의 핵심은 단순히 영상 위에 임시 화면을 덮는 것이 아니라, **사용자가 화면에 도착하기 전에 필요한 재생 상태를 준비하는 것**이었습니다. 조작 안내 역시 애니메이션 자체보다 사용자가 해야 할 행동을 분명히 드러내는 방향으로 정리했습니다.

최종 v32는 배포와 사용자 확인을 마쳤으며, 코드·작업 일지·참고 자료를 함께 관리해 다음 행사나 부서 공유에 활용할 수 있도록 했습니다.
