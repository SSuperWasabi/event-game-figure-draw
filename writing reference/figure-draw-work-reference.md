## 2. 프로젝트 출발과 운영 구조

기존 KUJI v31을 기반으로 사내 피규어 배포 이벤트용 Figure Draw PWA를 분리했다. 기존 앱과 브라우저 데이터가 충돌하지 않도록 localStorage, IndexedDB, Service Worker의 앱 식별 체계를 분리했다.

기본 경험은 메인 화면 → 소환서 조작 → 소환 연출 → 당첨 또는 미당첨 결과 → 메인 복귀다. 관리자 설정, 상품 재고, 추첨 기록, 미디어와 백업 기능을 유지하면서 이벤트 연출과 iPad 동작을 보완했다.

## 3. 소환서 인터랙션과 오디오

- 손가락 또는 포인터를 오른쪽으로 움직이는 진행도와 소환서 영상의 전개를 연결했다.
- 되돌리기·중도 취소를 처리하고, 소환 완료 전에 추첨이나 재고 차감이 일어나지 않도록 검증했다.
- 자동 오픈 경로의 1.8배속 재생과 사용자 드래그 경로를 함께 유지했다.
- 영상 끝부분에서 재시작하거나 이전 프레임이 노출되는 문제, 되감기 완료 전의 잔상과 전환 화이트아웃을 보완했다.
- 차가운 미디어 로딩 상태에서도 제스처와 재생 준비가 끊기지 않도록 준비 상태를 정리했다.

iPad 재생 문제는 v8·v9·v11 비교 테스트로 분리해 확인했다. 해당 소환서 미디어의 H.264 레벨·타임베이스 문제를 다루고, v12에서 30fps / H.264 High Level 3.1 호환 인코딩을 적용했다. 과거 미디어의 Level 6.2 및 타이밍 문제를 모든 영상 지연의 단일 원인으로 일반화하지 않는다.

오디오는 Web Audio를 이용한 BGM 덕킹과 효과음 재개를 보완했다. 소환 시 BGM을 25% 수준으로 낮추는 경로, 역방향 조작의 오디오 처리, 자동 오픈의 공유 오디오 경로를 정리했다. 단일 BGM 반복 옵션과 화면 이동 중 BGM 연속성도 포함한다.

## 4. 화면 구성과 드래그 안내 UI

영상 방향과 화면 비율에 맞춰 메인 타이틀 구성을 조정했다. LUCKY DRAW / EVENT / TOUCH 안내, 미당첨 문구, 관리자 선택 단계 생략 설정 등의 이벤트 흐름도 정리했다.

드래그 안내는 사용자가 조작할 대상과 움직일 방향을 분명히 알 수 있도록 반복 수정했다.

- 안내 UI를 소환서 화면 박스 내부 하단에 배치했다.
- 약 75% 불투명도, 보라색 캡슐 핸들, 그립 표시와 골드 이중 화살표를 적용했다.
- 레일 화살표를 5개에서 10개로 늘려 간격을 촘촘하게 했다.
- 레일 화살표 stroke는 기존 대비 1.5배인 12px로 보강했다.
- 자동 오픈 버튼 위 안내 문구 크기를 기존 대비 150%로 키웠다.
- **대기 상태에서는 핸들이 왼쪽 출발점에 고정된다.** 실제 터치 드래그 때만 진행도에 따라 움직인다.
- 골드 레일 화살표만 자동차 시퀀스 방향지시등처럼 왼쪽에서 오른쪽으로 순차 점등한다.
- 동작 줄이기 설정을 고려한 표현도 유지했다.

핵심 결정은 대기 애니메이션이 조작 대상 자체를 자동 이동시키지 않도록 하는 것이다. 사용자는 왼쪽 끝에서 드래그를 시작하고, 순차 점등은 방향 안내만 담당한다.

## 6. 메인 루핑 영상 개선 이력과 최종 방식

### 문제와 목표

메인 복귀 시 영상 데이터가 있어도 첫 화면이 늦게 나타났다. 당시 확인한 메인 영상은 약 30~47초, 35~40MB 수준으로, 파일 읽기뿐 아니라 Blob 연결과 첫 프레임 디코딩도 준비 비용에 포함됐다.

사용자가 정한 목표는 **메인에 들어오는 순간부터 다음 영상이 나오는 경험**이다. 포스터나 이전 영상을 먼저 보여 준 뒤 교체하는 연출은 목표에 맞지 않아 제외했다.

### 시도와 결정

| 단계 | 작업 | 판단 |
| --- | --- | --- |
| v25 | 한 순환 안에서 중복 없는 영상 셔플 및 순환 경계 중복 방지 | 최종 유지 |
| v28 | 배경용 중복 영상 재생 제거, 작은 정지 이미지로 레터박스 배경 처리 | 최종 유지. 전경 시작 포스터와는 다른 용도 |
| v29 | 첫 영상 데이터 읽기 우선순위 및 미리 읽기 개선 | 데이터 준비만으로 디코딩 지연까지 해결되지는 않음 |
| v30 | 초기 포스터 및 직전 첫 프레임으로 지연을 가리는 방식 | 사용자 경험에 맞지 않아 최종 방식에서 제외 |
| 검토안 | 이전 영상 잠깐 재생 후 다음 영상 전환 | 사용자 요청에 따라 제외 |
| v31 | 다음 영상을 화면 복귀 전에 디코딩하고 준비된 플레이어 재사용 | 최종 적용 |

### v31 최종 구조

두 개의 고정 video 요소를 사용해 현재 영상과 다음 영상을 관리한다. 현재 메인 영상이 재생되는 동안부터 다음 영상의 시작 프레임을 준비하고 0초 위치로 미리 정렬한다. 준비된 상태로 메인에 복귀하면 같은 요소와 소스를 사용하므로 복귀 순간의 불필요한 `src` 재연결, `load()`, seek를 피한다.

숨은 다음 영상을 계속 루핑시키는 방식은 아니다. 중복 초기화와 비동기 준비의 오래된 결과가 새 상태에 반영되는 경로도 정리했다. 기존 KUJI와의 비교를 참고하되, 단순히 `pause()` 한 줄이나 파일 용량만을 모든 지연의 원인으로 단정하지 않았다.

전경 포스터나 이전 영상의 잠깐 노출은 해결책에 포함하지 않는다. 브라우저가 리소스를 회수했거나 첫 실행에서 데이터가 아직 없는 경우까지 지연 0을 보장하는 것은 아니다.

## 7. 미당첨 결과 영상 개선 — v32

### 반복 지연의 원인

미당첨 영상은 한 종류인데도, 결과 진입 시 미디어 읽기 → Blob URL 연결 → video 생성 → 디코딩을 반복하고 화면을 떠날 때 준비 상태를 해제하는 경로가 있었다. 파일이 저장되어 있다는 사실만으로 다음 결과 화면의 디코딩 준비까지 유지되지는 않았다.

### 적용 내용

- 단일 미당첨 영상용 플레이어를 지속적으로 재사용한다.
- 결과 카드가 다시 만들어져도 영상 노드는 유지되도록 별도 위치에서 관리한다.
- 메인 영상 준비를 먼저 처리한 뒤 미당첨 영상 준비를 진행한다.
- 결과 진입 전에 정지·시작 위치 준비를 마치고, 준비된 결과 진입 시 다시 로드하거나 seek하지 않는다.
- 화면 밖에서는 불투명 덮개와 비활성 상태를 적용해 영상 노출과 불필요한 결과 UI 애니메이션을 방지한다.
- 미디어 키 변경, 파일 교체, 오래된 비동기 준비 요청은 취소·무효화한다.
- 단일 미당첨 영상 조건에 한정하며, 여러 영상 등 다른 조건은 기존 경로로 처리한다.

### 보존한 동작

결과 진입부터 계산하는 5초 자동 복귀, 팝업 동작, 음소거, 메인 영상 순서, 추첨·재고·로그 처리와 관리자 설정을 유지했다. 타이머 기준을 영상 `playing` 이벤트로 옮겨 결과 체류 시간을 바꾸는 방식은 사용하지 않았다.

## 9. 작업 폴더·리소스·공유 정리

- 작업 기준 폴더를 C:에서 `F:\Download\Figure draw app`으로 이전했다. C: 원본 삭제가 불가능하면 남겨 두라는 사용자 지시가 있었으며, 이 문서는 원본 삭제 성공을 새로 주장하지 않는다.
- 리소스는 이미지·영상·오디오·폰트 등 유형별로 분류하고, 최종본과 이전 후보를 `final-assets` 및 `-old`로 나눴다.
- `generated-candidates`를 이름만 보고 구버전으로 분류했던 점은 사용자 피드백으로 정정했다. 메인 루핑·미당첨 최종 영상은 `resource\videos\final-assets` 범주로 관리한다.
- 실제 배포 자산은 `app/assets`를 기준으로 한다. 대용량 `resource` 및 운영 백업은 Git 제외 대상이므로, GitHub 소스 공유와 전체 폴더 공유는 포함 범위가 다르다.
- 기존 `Figure-draw-app-v28-share.zip`은 이번 문서 정리에서 재생성하지 않았다. **이전 ZIP을 v32 최신 패키지로 전달하지 않는다.** 공유 시 최신 파일과 필요한 운영 자산의 포함 여부를 확인한다.
- 로컬 HTML 파일 경로와 웹에서 열리는 HTTP 미리보기 링크를 구분한다. 공개 앱 확인은 위 GitHub Pages 주소를 이용한다.

채팅 표시 문제와 앱 코드 문제는 별개다. 이 자료는 작업 이력의 지속 가능한 기록을 제공하지만, 과거 채팅 유실 원인 규명이나 원문 복구 완료를 뜻하지 않는다.

## 11. 인수인계 및 후속 변경 주의

1. 실행은 GitHub Pages 앱 주소로 안내하고, 코드 참고는 저장소와 README를 제공한다.
2. 상품·미디어·재고·추첨 기록 등 운영 데이터는 기기 브라우저 저장소에 의존한다. `.kuji` 백업을 별도로 관리한다.
3. 여러 기기의 재고가 자동으로 동기화되는 중앙 서버 서비스나 서버 기반 1인 1회 통제로 설명하지 않는다.
4. PWA 업데이트 확인을 위해 운영 데이터가 들어 있는 사이트 저장소를 무작정 삭제하지 않는다.
5. 다음 기능 변경에서는 앱 버전과 Service Worker 버전을 함께 검토한다. 이번 문서 전용 변경은 v32를 유지한다.
6. 영상 교체·추첨 설정 변경 후에는 메인 복귀, 연속 미당첨, 드래그 취소, 자동 오픈, 팝업 및 자동 복귀를 다시 확인한다.

컨플루언스에는 별도 게시용 원고를 사용하고, 이 문서는 세부 이력과 근거를 확인하는 writing reference로 연결한다.
